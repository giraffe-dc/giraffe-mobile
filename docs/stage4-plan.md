## 2. Оцінка пунктів Етапу 4

### 2.1 `expo-updates` / EAS Update — 🔴 заблоковано (акаунт)

- **Що дає:** OTA-фікси JS-коду без перезбірки APK і без оновлення через Releases.
- **Що потрібно:** акаунт Expo → `eas init` (projectId) → `expo-updates` + `eas.json` →
  `runtimeVersion` (рекомендовано `{ "policy": "appVersion" }`, щоб OTA не потрапляв
  на несумісну нативну збірку) → `channel: production` → перезбірка APK → `eas update`.
- **Важливо:** OTA **не може** змінити нативний код. Push, гео, календар, haptics
  і будь-який новий модуль як і раніше вимагають повної збірки (~19 хв).
- **Проміжне рішення без акаунта:** залишити чинний канал — версія в БД сайту +
  GitHub Releases + модалка «Доступна нова версія». Це вже працює й не вимагає деплою.
- **Коли акаунт з'явиться:** той самий projectId одразу розблокує **push-токени**
  (зараз `getExpoPushTokenAsync()` кидає `ERR_NOTIFICATIONS_NO_EXPERIENCE_ID`,
  ми тихо це пропускаємо) — тобто EAS-проєкт вирішує два пункти за раз.

### 2.2 Аналітика воронки + Sentry — 🟑 частково (власна воронка — можна, Sentry — ні)

**Власна аналітика (без зовнішніх сервісів):**

- Події: `catalog_view`, `service_view`, `calc_start`, `calc_finish`,
  `assistant_start`, `assistant_finish`, `booking_open`, `booking_submit`,
  `order_confirmed` (останню генерує сайт при зміні статусу на `confirmed`).
- Схема події: `{ event, ts, deviceId, platform, appVersion, props }`.
  **Заборонено** зберігати телефон, ім'я, адресу чи текст заявки — лише
  випадковий `deviceId` в AsyncStorage (і `orderId` для `order_confirmed`).
- Бекенд сайту: `POST /api/mobile/events` (батч, rate-limit, CORS, валідація
  enum-подій) → колекція `mobile_events`; `GET /api/admin/analytics/funnel`
  (тільки `verifyAdmin`) → лічильники по подіях і конверсія між етапами.
- Клієнт: черга подій у AsyncStorage, flush батчем при появи мережі/раз на
  30 с, **тільки за наявності згоди на аналітику**. Поважати `enabled: false`
  і видаляти чергу при відкликанні згоди.
- Адмінка: `/admin/analytics` — таблиця воронки за 7/30 днів, у стилі
  наявних `/admin/stats`. Окремий мобільний адмін-інтерфейс не потрібен
  (рішення власника ще з Етапу 3).
- Орієнтовний обсяг: 1–1.5 дня бекенд + 0.5 клієнт + 0.5 адмінка.

**Sentry:** 🔴 потрібен акаунт, DSN, source maps і release tracking. Без нього —
опційний власний `POST /api/mobile/errors` (санітизований stack + версія застосунку,
без PII, з тією самою згодою) і перегляд у `/admin/analytics`. Рішення власника —
чи потрібний цей замісник, чи дочекатися Sentry.

### 2.3 EAS Build — 🔴 заблоковано (акаунт)

- Замінює локальний `subst C:\g` + Gradle на хмарну збірку; прибирає 19-хвилинне
  очікування й проблеми з довгими шляхами Windows.
- Після появи акаунта: `eas.json` (профілі `production` / `development`),
  `eas build -p android --profile production`, облікові дані підпису — в EAS.
- Дистрибуція лишається незмінною: APK завантажується з Releases, сайт — лише
  маніфест версії. **APK не зберігаємо в git/Vercel** (ліміти розміру).
- Побічна вигода: EAS-проєкт дає `projectId` → push і OTA (див. 2.1).
- Дрібний технічний борг, який варто закрити незалежно від EAS:
  `scripts/build-apk.ps1` у PowerShell 5.1 падає через UTF-8 без BOM
  (обійшлися тимчасовою копією з BOM) — переписати запис файлів через
  `UTF8Encoding($true)` у самому скрипті.

### 2.4 Екрани згоди й політика конфіденційності — 🟢 можна зараз

- Зразок на сайті: `CookieBanner.tsx` (згода зберігається в localStorage),
  `ConsentAnalytics.tsx` (аналітика не завантажується без згоди), `/privacy`.
- У додатку: окремий екран «Приватність» (доступний з кабінету та першого запуску):
  - аналітика — **вимкнено за замовчуванням** (opt-in);
  - push — окремийtoggle; запит дозволу не робити до явної згоди;
  - геолокація — окремийtoggle; наразі запит іде по кнопці, але перед ним
    має бути пояснення, навіщо вона потрібна;
  - посилання на повний текст `https://giraffe-teplyk.vercel.app/privacy`
    через `Linking.openURL` (без нового `expo-web-browser`);
  - зберегти в AsyncStorage `giraffe-privacy-consent-v1` разом із `updatedAt`,
    можливість змінити рішення в будь-який момент.
- Сторінка `/privacy` на сайті вже є — окремий API не потрібен; якщо колись
  знадобиться офлайн-текст — додати `/api/data/privacy` і фолбек у додатку.
- Обсяг: 0.5–1 день. PWA отримає зміни одразу після деплою; APK — з наступною
  плановою збіркою (разом з іншими накопиченими JS-змінами).

### 2.5 Доступність — 🟡 частково

| Підпункт | Можливість | Коментар |
|---|---|---|
| Великі шрифти | 🟢 зараз | `AccessibilityProvider` з коефіцієнтом 1.0 / 1.15 / 1.3; застосувати до основних екранів через новий хук `useFontScale()`, не переписуючи всі стилі одразу |
| Контраст | 🟢 зараз | Токен контрасту в тому ж провайдері (наприклад, `muted` → `ink`, межі → темніші). Потребує акуратного проходу по `COLORS.*`, бо зараз це `const` |
| Dark mode | 🟡 «за бажанням» | Вимагає заміни `COLORS` на провайдер теми або mutable-об'єкт; ризик регресій у всьому UI. Рекомендую відкласти до окремого етапу й не робити разом із іншими змінами |
| Haptics | 🔴 після збірки | `expo-haptics` — нативний модуль; додати разом з `expo-updates` в одну перезбірку APK |

## 3. Рекомендована послідовність (без акаунтів)

**Фаза A — власними силами (пріоритет):**
1. Екран згоди + налаштування приватності (2.4).
2. Власна аналітика воронки: `/api/mobile/events`, `/api/admin/analytics/funnel`,
   клієнтська черга з валідацією згоди, `/admin/analytics` (2.2).
3. Доступність: великі шрифти й контраст (2.5), без dark mode.
4. (Опційно) власний збір помилок замість Sentry — за окремим рішенням власника.

**Фаза B — після появи акаунта Expo:**
`eas init` → `EXPO_PUBLIC_PROJECT_ID` → `expo-updates` + `eas.json` →
`expo-haptics` → одна перезбірка APK → OTA-канал і push стають активними.

**Фаза C — після появи акаунта Sentry:**
DSN, source maps, release tracking; за потреби прибрати власний error-ендпоінт.

Кожна фаза завершується окремою перевіркою: `npx tsc --noEmit` (сайт),
`npm run ts:check` (додаток), `npm run export:pwa`, новий `scripts/test-stage4.mjs`
і — тільки у Фазі B — повною збіркою APK.

## 4. Ризики й мітигації

| Ризик | Мітигація |
|---|---|
| OTA не доставляє нативні зміни | Чітко розділити JS- і native-зміни; для нативних — завжди Releases + SDK-версія в маніфесті |
| Аналітика збереже PII | Схема подій без телефону/імені/адреси, enum подій, валідація на сервері, згода за замовчуванням вимкнена, періодичне очищення старих подій |
| Воронка «ламається» при зміні екранів | Події описувати в одному файлі-константі, тестувати enum і конверсію на тестових даних |
| Android APK росте (зараз 76.3 МБ) | Не додавати зайві модулі; haptics і updates — лише в одній фінальній збірці |
| Push мовчки не працює без projectId | Явне повідомлення в налаштуваннях: «Потребує EAS-проєкту»; у docs — вже зафіксовано |
| Збірка падає через UTF-8 у PowerShell 5.1 | Виправити `build-apk.ps1` (BOM) до наступної збірки, не покладатися на тимчасову копію |
| Vercel Cron без секрета | Задати `CRON_SECRET` (або покластися на fallback `MOBILE_RELEASE_KEY`) — вже в README |
| Dark mode затягне регресію UI | Не робити в цій фазі; окремий етап із скріншотами |

## 6. Критерії готовності Етапу 4 (після реалізації)

- Клієнт бачить і змінює згоду на аналітику/push/гео в додатку, текст `/privacy` доступний з додатка.
- Аналітика не надсилає жодної події без згоди; у адмінці є воронка «перегляд → калькулятор → заявка → підтвердження».
- Шрифти й контраст масштабуються без ламання екранів; PWA й APK проходять `ts:check` і `export:pwa`.
- (Після акаунта) OTA-оновлення застосовується без нового APK; EAS Build замінює локальний Gradle.
