> Повернутися до [README.md](README.md). Шляхи в документі вказані відносно кореня робочої теки `Giraffe+`.

**Дата:** 2026-11-19
**Статус:**
- **Етап 0 (інфраструктура дистрибуції) реалізовано** — `/api/mobile/version`, сторінка `/app`
  з QR-кодом, APK у **GitHub Releases** (не в git/Vercel — ліміти розміру), перевірка оновлень
  у додатку, скрипт `scripts/build-apk.ps1` + `upload-release.mjs`.
- **Етап 1 (PWA для iPhone) реалізовано** (локально): web-експорт `npm run export:pwa` → `dist/`,
  `+html.tsx` (Apple/manifest-метатеги), `manifest.webmanifest`, `sw.js`, іконки,
  `vercel.json`; локально перевірено (18 маршрутів, SW активний). Публікація — коли з'явиться
  Vercel-проєкт із Root Directory `giraffe-mobile`.
- **Етап 2 (функціонал) реалізовано:** калькулятор «Збери сам» (`app/calculator.tsx`),
  підбір програми (`app/assistant.tsx`), FAQ (`app/faq.tsx`), галерея з альбомами і SVG

  (`app/book.tsx`, схема `giraffe` в `app.json`), сезонний банер і швидкі дії на головній,
  форма відгуку + розгорнуті новини в контактах, CORS для `POST /api/reviews` на сайті.
  `tsc` чистий, web-експорт і локальний рантайм перевірено в браузері.
**Залишилося (Етап 2 → фініш):** задеплоїти `giraffe-site` (CORS відгуків, нові секції),
створити Vercel-проєкт PWA і вказати домен у `NEXT_PUBLIC_PWA_URL`, перевірити `POST /api/reviews`
з origin PWA, фінальна перевірка на реальному iPhone, зібрати APK v1.0.3 (нові нативні
залежності `react-native-svg`, `async-storage` не потрапили у v1.0.2).
**Контекст:** готовий Expo/React Native додаток у `giraffe-mobile`, зібраний release APK (64,5 МБ),
реальний бекенд у `giraffe-site` (Next.js + MongoDB). APK роздається клієнтам напряму
(посилання зі сторінки `/app`) — **без Google Play / App Store**.

| Варіант | Вартість | Що дає | Недоліки |
|---|---|---|---|

## Етап 0. Інфраструктура дистрибуції (3–5 днів, критичний шлях)

**Мета:** APK + версія + сторінка завантаження + перевірка оновлень.

### Задачі

1. **Релізний ключ замість debug**
   - згенерувати `release.keystore`, додати `android/keystore.properties` (у `.gitignore`);
   - налаштувати `signingConfigs.release` у `android/app/build.gradle`;
   - зібрати APK під релізним ключем. Критично: втрата ключа = неможливість оновити додаток.
2. **Хостинг APK — GitHub Releases (замість сайту)**
   - ⚠️ Рішення власника (2026-11-19): APK **не** зберігати в git (GitHub лімітує файл 50 МБ)
     і на Vercel (обмеження деплою). Дистрибуція — через GitHub Releases
     `giraffe-dc/newSite`, тег `v<versionName>`, ассет `giraffe-mobile-<версія>-b<build>.apk`;
   - `giraffe-mobile/scripts/upload-release.mjs` створює release і завантажує ассет
     (аутентифікація через git credential helper), `build-apk.ps1` викликає його автоматично;
   - `giraffe-site/public/app/` містить лише `version.json` — **fallback**, коли БД порожня
     (`.gitignore`: `public/app/*.apk`);
   - SHA-256 контрольна сума на сторінці `/app` — для перевірки цілісності.
3. **Маніфест версії**
   - публічний `GET /api/mobile/version`: `{ versionName, versionCode, apkUrl, changelog, publishedAt }`;
   - ⚠️ Рішення власника (2026-11-20): джерело істини — **БД сайту** (колекція
     `mobile_releases`, `_id: "current"`), а не static-файл: скрипт збірки публікує
     версію через `POST /api/mobile/version` (API-ключ `MOBILE_RELEASE_KEY`),
     тому **реліз додатка не вимагає деплою сайту**;
   - реалізація — `src/lib/mobileRelease.ts` (читання БД → fallback на файл,
     сувора валідація маніфеста при записі);
   - CORS `*` (для PWA).
4. **Сторінка `/app` на сайті**
   - QR-код на APK (бібліотека `qrcode` або згенерований SVG), кнопка «Завантажити Android»;
   - блок «Для iPhone» з інструкцією Safari → «Поділитися» → «На головний екран»;
   - покрокова інструкція для Android: «Дозволити встановлення з невідомих джерел»;
   - телефон/Telegram для питань.
5. **Перевірка оновлень у додатку**
   - додати `expo-application`;
   - у `src/api/client.ts`: `fetchAppVersion()`;
   - у `app/_layout.tsx`: при старті порівняти `nativeBuildVersion` з `versionCode` з API,
     показати модалку «Доступна нова версія» → `Linking.openURL(apkUrl)`;
   - не блокувати роботу додатка, якщо API недоступне.
6. **Скрипт збірки** `giraffe-mobile/scripts/build-apk.ps1`
   - `subst G:` → `gradlew assembleRelease` → завантаження у GitHub Releases →
     публікація маніфесту в БД сайту (`scripts/publish-version.mjs`) → друк SHA-256;
     деплой сайту після релізу не потрібен.
   - прибрати тимчасові копії `package.json`/`app.json` в `android/` після переходу на EAS (пізніше).

**Критерії прийняття:** APK встановлюється на реальний телефон; на сайті є QR і обидві інструкції;
додаток повідомляє про нову версію, якщо `versionCode` у маніфесті більший.

## Етап 3. Кабінет, бекенд і нативні можливості (14–20 днів)

1. ✅ **Кабінет клієнта з історією заявок** — **виконано 2026-11-20**.
   - легка авторизація за номером телефону: `POST /api/mobile/auth/request-code` +
     `POST /api/mobile/auth/verify`, 6-значний код надсилається через наявний Telegram-бот/чат

     `GET /api/mobile/orders` — **тільки свої** заявки (за телефоном із токена, старі формати номерів підтримуються);
   - вкладка «Кабінет»: список заявок зі статусами **`new → in_progress → confirmed → done / cancelled`**
     (це реальні статуси адмінки сайту; roadmap-значення `on_the_way` не існує в бекенді),
     дата, адреса, обрана програма, деталі по кліку; кнопки «Написати в чат», «Додати в календар»,
     «Повторити замовлення» — у наступних підпунктах Етапу 3;
   - статуси й дані модеруються **через адмінку сайту** — окремого мобільного адміна не потрібно.

2. ✅ **Зайняті дати — попередження, не блокування** (рішення власника) — **виконано 2026-11-20**
   - `GET /api/mobile/busy-dates` — публічний список дат без персональних даних;
   - у виборі дати: жовтий badge і повідомлення
     «На цю дату вже є інше замовлення. Адміністратор зв'яжеться для уточнення деталей»;
   - **дату можна обрати й заявка надсилається звичайно** — блокування заборонено.
3. ✅ **Push-нагадування** — Expo push-токен реєструється після OTP-входу (`POST /api/mobile/push-token`, колекція `push_tokens`), надсилання — у `src/lib/pushNotifications.ts`. Події: зміна статусу (admin PATCH), за 1 день і запит відгуку (`GET /api/cron/push-reminders`, Vercel Cron 07:00 UTC у `giraffe-site/vercel.json`). 4. ✅ **Геолокація** — `src/services/geo.ts` (expo-location): відстань від Теплика, тариф × км із каталогу, попередження про >40 км без блокування заявки.
5. ✅ **Календар** — `src/services/calendar.ts` (expo-calendar): кнопка в деталях заявки додає подію з нагадуванням за 24 год; у PWA прихована.

7. ✅ **Опитування** — `src/components/SurveyCard.tsx` у розгорнутій новині: голосування за варіанти (`/api/survey/vote`) або довільні поля (`/api/survey/submit`), результати — `/api/survey/results`; CORS для PWA додано.

## Прийняті рішення (відповіді власника, 19.11.2026)

1. **Apple Developer Program:** немає й не планується → iOS-канал тільки PWA (Етап 1), TestFlight не робитимемо.
2. **Кабінет клієнта:** додаємо → історія заявок і статуси входять в Етап 3; потрібна легка авторизація за телефоном.
3. **Модерація й зв'язок:** відгуки та інші дані — через адмінку сайту; чат із клієнтом — аналогічний сайту
   (наявний `/api/chat*` + `/admin/chat`). Окремого мобільного адмін-інтерфейсу не створюємо.
4. **Зайняті дати:** показуємо публічно, **але не блокуємо** бронювання — повідомлення
   «На цю дату є інше замовлення, адміністратор зв'яжеться для уточнення деталей».
